**데이터 규모**
- 시뮬레이터 생성 이벤트: 3,161건
- 정답 라벨: 14건
- 분석 시나리오 관련 이벤트: 3건

**시간순 이벤트**

| 시각 (UTC) | 이벤트 ID | 유형 | 관찰 내용 |
|---|---|---|---|
| 09:41:42 | `evt-00003002` | process | `cmd.exe` 실행, PID 37467, PPID 1653 |
| 09:41:43 | `evt-00003003` | process | `rundll32.exe` 실행, PID 51765, PPID 37467 |
| 09:41:44 | `evt-00003004` | file | `rundll32.exe`가 `C:\Windows\Temp\d.dmp` 파일 생성 |

**프로세스 계보**

```text
explorer.exe (PID 1653, 실행 이벤트 미확인)
└── cmd.exe (PID 37467)
    └── rundll32.exe (PID 51765)
        └── d.dmp 파일 생성
```

**관찰과 판단**

`rundll32.exe`가 `comsvcs.dll`의 `MiniDump` 기능을 호출하는 명령을 실행했으며, 이후 같은 PID에서 덤프 파일 생성 이벤트가 확인되었다.

정답 라벨은 해당 시나리오를 `malicious: true`, `T1003.001`로 표시한다. 이는 시뮬레이터의 정답이며, AI가 독립적으로 판정한 결과는 아니다.

**설계 결정 및 한계**

- 이벤트를 `event_id`와 `host`로 연결하고, `ts` 순서로 정렬해 조사한다.
- `pid`와 `ppid`를 비교해 부모·자식 관계를 추적한다.
- 부모 `explorer.exe`의 실행 이벤트는 검색 결과 0건으로 확인되지 않았다.
- 따라서 부모 이벤트가 존재한다고 가정하지 않고, 자식 이벤트의 `parent_name`과 `ppid`를 참고 정보로 활용한다.
- 향후 프로세스 트리 조사 도구는 부모 이벤트가 누락되어도 조회가 실패하지 않도록 설계할 필요가 있다.

**선택한 방법과 포기한 것**

외부 정보로 누락된 이벤트를 추정해 채우는 대신, 현재 데이터셋에서 확인한 이벤트 3건과 부모 이벤트 미확인 사실을 그대로 기록하기로 했다. 이를 통해 조사 결과와 추정을 구분할 수 있다.

### text vs keyword (1일차)
<!-- 03 문서 1장의 질문에 대한 내 답과, 실제로 정한 매핑 -->


#### 1. 설계 목적 및 교안 질문

**Q1. 호스트 이름(`WS-007`)은 `text`와 `keyword` 중 무엇으로 저장해야 할까? 왜?**

호스트 이름은 `keyword` 타입으로 저장하는 것이 적절하다.

`text`는 문장을 분석하여 단어 단위로 검색할 때 사용하지만, `keyword`는 문자열 전체를 하나의 값으로 취급하여 정확히 일치하는 검색에 적합하다.

EDR에서는 특정 PC의 보안 이벤트를 정확하게 조회해야 하므로 `host`를 `keyword`로 매핑했다.

반면 명령줄(`process.cmdline`)처럼 내부의 특정 단어를 검색해야 하는 필드는 `text`가 필요하다. 명령줄 전체의 정확한 일치 검색도 필요하므로 `text`와 `keyword`를 함께 사용했다.

**Q2. "WS-007에서 09:00~09:30 사이에 일어난 일"을 찾으려면 어떤 검색 두 가지를 섞어야 할까?**

`term` 쿼리와 `range` 쿼리를 함께 사용한다.

- `term`: 호스트 이름이 `WS-007`인 이벤트를 정확하게 찾는다.
- `range`: 이벤트 발생 시간이 09:00~09:30에 해당하는 기록을 필터링한다.
- `bool.filter`: 두 조건을 동시에 만족하는 이벤트만 조회한다.

이를 통해 특정 PC에서 지정한 시간에 발생한 보안 이벤트만 조회할 수 있다.

> `term`과 `range`를 결합한 검색은 설계 개념을 정리한 것이며, 실제 실행 검증은 아직 진행하지 않았다.

#### 2. 실제 매핑 결정

EDR 이벤트의 필드별 특성과 검색 목적에 따라 OpenSearch 매핑을 구분했다.

| 필드 | 매핑 | 선택 이유 |
|---|---|---|
| `event_id` | `keyword` | 이벤트 식별자 정확 일치 검색 |
| `host`, `type`, `process.name` | `keyword` | 정확한 값으로 필터링 |
| `ts` | `date` | 시간 범위 조회와 정렬 |
| `process.pid`, `process.ppid` | `long` | 정수 기반 조회 및 프로세스 관계 추적 |
| `network.dst_ip` | `ip` | IP 주소 검색 |
| `network.dst_port`, `network.bytes_out` | `long` | 포트 번호 및 전송량 조회 |
| `process.cmdline`, `script_text` | `text` + `keyword` | 내부 단어 검색과 전체 값 일치 검색 지원 |

**인덱스 템플릿 설정**

- 템플릿 이름: `edr-events`
- 적용 패턴: `edr-events-*`
- 샤드 수: `1`
- 복제본 수: `0`
- 매핑 설정: `dynamic: strict`
- 명령줄과 스크립트: Multi-fields 방식으로 `text`와 `keyword`를 함께 지정

#### 3. 실제 검증 결과

**① 템플릿 등록 및 데이터 적재**

- `.env`에서 `BACKEND=real` 설정
- Python 클라이언트가 실제 `OpenSearch` 객체임을 확인
- OpenSearch 템플릿 `edr-events` 등록 및 HTTP API 조회 성공
- 기존 `edr-events-*` 인덱스 수: 0개
- 원본 이벤트 수: 3,161건
- OpenSearch 적재 건수: 3,161건
- 적재 후 전체 문서 수: 3,161건

**② text와 keyword 검색 비교**

| 검색 방식 | 검색 조건 | 실제 결과 |
|---|---|---:|
| `term` / keyword | `host=WS-006` | 349건 |
| `match` / text | `process.cmdline`에서 `MiniDump` 검색 | 4건 |
| `term` / keyword | `process.cmdline.keyword`에서 `MiniDump` 검색 | 0건 |
| `term` / keyword | `process.cmdline.keyword`에서 전체 명령줄 정확 일치 검색 | 4건 |

**③ 검색 결과 해석**

실제 조사한 `credential_dump` 시나리오의 명령줄은 다음과 같다.

```text
rundll32.exe C:\Windows\System32\comsvcs.dll, MiniDump 668 C:\Windows\Temp\d.dmp full
```

- `text` 필드에서는 `match` 쿼리를 사용하여 긴 명령줄 내부의 `MiniDump`를 검색할 수 있었으며, 4건이 조회되었다.
- `keyword` 필드에서는 `term` 쿼리로 `MiniDump`만 검색했을 때 명령줄 전체와 일치하지 않아 0건이 조회되었다.
- `keyword` 필드에서 전체 명령줄을 입력했을 때는 정확하게 일치하는 이벤트 4건이 조회되었다.

단, 위 명령줄 검색에는 호스트 필터를 적용하지 않았으므로 조회된 4건이 모두 동일한 호스트에서 발생한 이벤트라고 단정할 수 없다.

이를 통해 `text`는 내부 단어 검색, `keyword`는 전체 값의 정확 일치 검색에 적합하다는 점을 실제 데이터로 확인했다.

#### 4. 설계 선택의 장점과 단점

**결정 1. 필드의 검색 목적에 따라 자료형 구분**

호스트명, 이벤트 유형, 프로세스명처럼 정확한 값으로 구분해야 하는 필드에는 `keyword`를 사용했다.

긴 명령줄과 스크립트는 내부 단어 검색과 전체 문자열 일치 검색이 모두 필요하므로 `text`와 `keyword`를 함께 사용했다.

- 장점: 조사 도구에서 단어 검색과 정확 일치 검색을 모두 지원할 수 있다.
- 단점: 단일 검색 방식보다 색인 및 저장 공간이 추가로 필요하다.

**결정 2. `dynamic: strict` 적용**

정의되지 않은 필드가 유입되면 자동으로 매핑을 생성하지 않고 색인을 거부하도록 설정했다.

- 장점: 예상하지 못한 데이터 구조나 필드 오류를 조기에 발견할 수 있다.
- 단점: 새로운 이벤트 필드가 추가되면 매핑도 함께 수정해야 한다.

#### 5. 최종 정리

EDR 조사에서는 **특정 호스트와 프로세스의 이벤트를 정확하게 찾는 검색**과 **명령줄 내부에서 의심스러운 단어를 찾는 검색**이 모두 필요하다.

따라서 정확한 값으로 필터링할 필드는 `keyword`, 긴 명령줄과 스크립트는 `text`와 `keyword`를 함께 사용하도록 설계했다.

실제 OpenSearch에 이벤트 3,161건을 적재하고 검색 결과를 비교하여 두 검색 방식의 차이를 검증했다.

이 설계를 바탕으로 다음 단계에서는 프로세스 계보, 프로세스 활동, 호스트 타임라인을 조회하는 조사 도구(REC-2~4)를 구현한다.
